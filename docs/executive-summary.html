2. Root-Cause Technical Analysis: Resolving "Predicted values must be in range [0, 1]"

The Problem: When downloading predictions from earlier sister repositories (such as GEMSDOE19, GEMSDOE24, GEMSDOE42, GEMSDOE49), users encountered the DrivenData upload error:

"Predicted values must be in range [0, 1]"

Why This Error Occurred: DrivenData's server-side validator executes an array validation equivalent to:

assert np.all((arr >= 0.0) & (arr <= 1.0)) and not np.isnan(arr).any() and not np.isinf(arr).any()
  • Out-of-Footprint NaNs: Many earlier submissions left pixels outside the competition study boundary as floating-point NaN (e.g. filenames containing -nan). The portal validator evaluates the entire raster bounding box and rejects any NaN as an out-of-range value.
  • GDAL Sentinel Values: Other runs wrote nodata sentinels (-9999.0 or -3.4028235e+38), which violate arr ≥ 0.0.
  • Unclipped Float Output: Regression outputs with unclipped logits or rounding overshoot (e.g. 1.0000001 or -0.0000001) trigger immediate portal rejection.

How GEMSDOE86 Solves This 100% by Construction:

  • All outside-footprint pixels are explicitly set to finite 0.0 with nodata = None.
  • Every inside-footprint value is strictly binary {0.0, 1.0} or bounded in [0.0, 1.0].
  • Zero NaNs, zero Infs, zero sentinels anywhere in the raster.
  • The serialization engine (vendor/gems57/submission_writer.py) validates all 15 format checks in memory and re-validates the serialized bytes from disk before publication.
